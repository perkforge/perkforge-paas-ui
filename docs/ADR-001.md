# ADR 001 — trusted UI workspace learning slice

Status: proposed. Date: 2026-10-27. Scope: standalone offline experiment in perkforge-paas-ui; no portal/platform changes.

## Decision and minimal plan

Use React/TypeScript, Zod runtime schemas, a pure reducer and one trusted CPU component. Start with a deterministic exact-phrase intent adapter and a fixed mock MetricsPort. Keep component code developer-owned. Do not install an agent framework until real provider/streaming requirements justify it. There is no graph yet and no need for a canvas dependency.

First slice: show three nodes → highlight/filter/sort same component → inspect evidence → dismiss/reset/error/repeated-request flows. Validate schemas, lint/types/build/unit tests, then desktop/mobile UI. One chart means no meaningful rearrangement yet. No infrastructure operations or credential handling.

## Candidates researched from primary documentation

Reviewed 2026-10-27; protocols evolve, so verify compatibility when integrating.

| Candidate                                    | Useful role later                                             | Why deferred now                                                                                                 |
| -------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| [CopilotKit](https://docs.copilotkit.ai/)    | React agent UI integration, shared state and human approvals  | No agent runtime/provider in this slice; adding it would obscure the small contract                              |
| [AG-UI](https://docs.ag-ui.com/introduction) | Event-based agent↔frontend transport and state/tool lifecycle | No streaming backend to transport; it is distinct from a UI component description                                |
| [A2UI](https://a2ui.org/)                    | Declarative UI messages and client-owned component catalogs   | A single fixed component needs only the local strict intent schema; this demo does not claim protocol compliance |
| [React Flow](https://reactflow.dev/learn)    | Node-based editors and interactive diagrams                   | CPU bars are not a topology editor; revisit for multi-resource relationships                                     |

The local architecture borrows the trusted-catalog principle without claiming any of these SDKs or protocols is installed.

## Three small tenant use cases to explore next

1. **Tenant health with evidence.** Ask for an authorized tenant's workloads, quota usage and recent failures. Present timestamped records and their source. Start with a mock composite health card and explicit missing/stale data states; read only.
2. **Tenant deployment self-service.** Approved image/environment/resource inputs → validated manifest diff → human-reviewed MR in the authorized tenant repository. This phase may only preview mock input/diff/review states. Never change tenant RBAC or network policies. Real repository writes require separately authorized scope, server validation and review; a chat request is not deployment authority.
3. **Rollout investigation.** Display observed rollout progress and events, separately labelled hypotheses and missing evidence. Start with a mock event timeline; no automatic restart/rollback. Each claim links to its source and sample time.

The CPU slice establishes the shared foundation: narrow intent, validated read contract, trusted view, visible evidence and deterministic follow-up state. The three cases are design candidates, not implemented features.

## Real integration boundary

A future server-side IntentProvider may call a real model and return the same untrusted schema. Validate again at the server and browser. A provider response selects an allowed action, never code or shell. If streaming is needed, consider AG-UI/CopilotKit after a separate ADR.

A future MetricsPort implementation should map a **confirmed** perkforge-portal API contract to this view model. No endpoint is assumed here. Add async loading, cancellation, stale/error/empty handling and tenant context after that API is known. Authorization belongs to the server: validate Keycloak issuer/audience/token, derive authorized tenant scope from verified identity, apply deterministic policy for every data/action request, and audit results. Browser filtering and model instructions are not authorization. Never embed provider secrets in the client. Human review supplements policy; it does not replace it.

## Tradeoffs / learning questions

The exact grammar is intentionally limited and explains unsupported requests honestly. Runtime schemas reject malformed structure but cannot establish semantic correctness or permission. Mock timestamps are fixed evidence, not freshness claims. Learn whether users value inspectable components before investing in agents, canvas layout, authentication or deployment automation. Preserve platform stability by keeping this experiment separate.
